# BitBurner consolidated rewrite execution plan

Authoritative execution plan prepared 2026-09-07 from the three independent plans and the revised `rewrite-direction.md`. Use this plan for sequencing; use `AGENTS.md` and the agent working agreement for project operating rules, with the user's latest instructions controlling scope and authority. `rewrite-plan-comparison.md` records what was adopted and corrected. This deliverable is planning only: it grants no current implementation, deployment, capital, reset or restricted-subsystem authority.

## 1. Outcome, full scope and staged delivery

Build one reliable control and observation foundation for **all current repository game capabilities**, including stock trading. Start with read-only evidence and the smallest owned process lifecycle; then migrate capabilities in bounded increments. Preserve valuable existing algorithms behind adapters until tests and outcome evidence justify change. A staged first release is not a reduced final scope.

Preserve the current repository, deployed source and runtime state. Legacy and rewrite must remain independently executable. Recommend a separate private rewrite repository/remote and a dedicated rewrite browser profile/save; namespace separation alone cannot isolate two active controllers competing on one save. The detailed isolation strategy below is a prerequisite, not an optional deployment refinement.

The system must explain what it observed and how fresh it is; what it intends and why; which authority permits each effect; which source/delivered/running generation is involved; what happened; whether the automation is worth its resource cost; and how to stop or revert it. These questions must be answerable from the operator surface and durable evidence without reverse-engineering code or reading a finite tail.

“All current capabilities” means every current automated, operator-invoked and experimental workflow discovered in this repository—not every hypothetical feature in Bitburner. No capability may disappear because its script is not in startup. Preserve the requested behavior through a new implementation, a tested adapter, or an explicit supported manual/proposal boundary. Duplicate and obsolete scripts can retire only after their behavior is accounted for. New batching, shorts, orders, game goals or unrelated game automation are not implied.

## 2. Corrected baseline and evidence limits

The comparison inspected repository source at HEAD `e7af653db93e366f72d0fcd98510d897bb001fa3` plus working-tree documents and retained telemetry. None of that proves an exact installed runtime release. Sol recorded 235 passing legacy Node tests and a passing Remote API self-test; this consolidation did not re-run them. B00 captures fresh reproducible baseline results and source hashes.

The evidence-driven starting decisions are:

- `sync_manifest.json` is a mutable file list, not a release digest. Python reads it at import, syncs individual files without complete readback, and browser startup fetches mutable `main` and launches after incomplete sync. Replace those activation assumptions, not necessarily the transports.
- `getWorkerHosts` explicitly excludes home. Retain a protected home control budget initially. R7's historic home allocation is not current behavior merely because `HOME_RAM_RESERVE` remains.
- Retained MCP events for run `mtrh1gm6-ig7p`, version `62f735`, contain finite-score R8 vetoes and subsequent allow/drop/re-adopt sequences (1161–1177). R8 is not “never fired”; its measured value and current environment identity remain unproved. The matching retained status resolves an active override to money. R6 still needs a current-release XP trial.
- Formula floor scoring already feeds primary ranking behind `FORMULA_RANKING_ENABLED`. R8 separately compares effective formula money scores after qualified switches and currently has no XP objective gate. Assess both the money-versus-XP mismatch and raw-outbid/effective-re-adoption mismatch before altering policy.
- Remote API retries/browser feasibility are unsettled across contradictory docs, code comments and upstream versions. Study a pinned game build. Do not assume either permanent browser impossibility or header-based success.
- Ordinary telemetry files can be stale, incomplete or overwritten; a process-level source hash does not identify its imports. Retained “live” evidence must acquire provenance before serving as a test fixture or promotion claim.
- Stock state and approval history conflict across dated documents. The revised instruction explicitly includes its full workflow in scope but grants no live capital authority. Existing code is evidence: preserve it while investigating accounting, dry-run budget allocation and actual order outcome semantics.

Use claim labels consistently: implemented, locally tested, integration-tested, browser-confirmed, Steam-confirmed, historical observation, assumed, or unresolved. A valid flag, successful file receipt, new PID, screenshot or passing mock is not a substitute for the next stronger claim.

### Runtime boundary and authority

Use an identified disposable browser profile/save for real game execution and failure injection. Keep browser and Steam storage, endpoint/ports, release channel, local telemetry root and startup profile separate. Record game version, profile/save marker, connection epoch and daemon identity before any write. A browser copy of a save may retain player identity, so distinguish it with a test marker as well. A test adapter must refuse the wrong/unknown environment before sync or activation; loopback and port numbers alone are insufficient.

Local unit/replay/protocol work proves only its stated abstraction. Browser evidence proves actual game behavior on its identified build and transport. Steam requires its own read-only/inactive-file transport check and shadow observation before one named capability acts. Do not induce disconnects, corrupt files, erase data, freeze UI or import saves in Steam as a test. Do not use the existing broad startup/manifest as the sandbox profile: it contains active and restricted capabilities.

Initial modes are observe, propose and paused. Acting names a specific capability, environment, allowed operations, budget and expiry; there is no global permission to do anything the API supports. Read-only process startup still changes the process list and needs the tested delivery path. A visible policy decision within existing user authority activates ordinary reversible behavior; do not create redundant approval gates. Current stock-capital, faction-share re-enable, augmentation install/reset/permanent-forfeiture boundaries remain explicit. Actual stock API-call implementation is also subject to the project's specific restriction on adding draft capital calls; initial stock packages use an inert interface and simulated executor. Historical approval is recorded with its scope and never silently expanded to a new strategy or liquidation.

One deterministic in-game effect owner reconciles authorized desired state. The local controller submits the same typed commands available in game and provides durable storage/proposals; it is not another independent supervisor. An optional AI steward may explain and propose, not invent goals, buy things, reset progress or change its own authority. Loss of the local observer does not require stopping safe in-flight workers. Loss of required fresh evidence blocks new dependent effects.

Shared worker RAM uses explicit leases/reservations so contracts and augmentation probes do not race MCP's refill loop. Shared cash uses a single budget/reservation view across stock, cloud and fee-bearing player activity. The player's activity and terminal connection have exclusive owners; manual use wins through a visible override. Plans revalidate actual resources at execution time and tolerate a foreign/manual change by reporting conflict, not killing it.

Recovery has a logical idempotency key, execution attempt IDs, preconditions, cooldown, deadline, attempts-per-window and total incident budget. Receipt, acceptance, start and completion are separate states. A timeout or crash after an effect means unknown until observed state reconciles it; no blind duplicate order, contract attempt, purchase or restart. Persist outcomes and cooldowns across restarts, scoped to save/session identity. Expired actions never execute after reconnect.

Pause stops new work; drain finishes authorized in-flight work within its deadline; emergency stop targets only verified owned processes; rollback activates the previous verified source and compatible desired state under a **new** runtime generation. It must not restore/import a Steam save. No technical rollback can reverse trades, contract attempts, purchases or forfeiture. Stopping stock automation preserves positions and displays them; liquidation is a separate explicitly authorized action. Retiring a process never erases accounting/evidence.

## 5. Shared foundation requirements

### Identity and deployment

The release manifest contains canonical paths, sizes and content digests for the complete dependency closure, schema/protocol compatibility and a release digest. Hash canonical content entries; exclude its own digest field and volatile build time from content identity. Source revision/build time are provenance, not substitutes for byte identity. Mutable runtime configuration and generated state are excluded from source sync; immutable defaults may be included.

Prepare an immutable release; stage to a non-active namespace; read back every file and verify its digest; activate only the complete verified set. Test actual Netscript path/import/RAM semantics before choosing namespace layout. If the game offers no atomic switch, specify the smallest interruption-safe sequence and prove its failure behavior. Never activate a mixed set or fall back silently to arbitrary stale files. Keep the prior verified release accessible.

Every resident process reports a boot-captured release and generation plus host/PID/start identity. Display source, delivered and all running values together, with unknown and drift explicit. Updating a shared manifest file cannot relabel a process. Reconciliation retires only superseded owned processes after confirming identity and exit; avoid global killall or each child killing peers. Fence reconnect-era requests to their connection and save; serialize delivery/control mutations to prevent overlapping resync loops mixing releases.

### State, control and events

Observed records carry schema version, environment/save epoch, occurrence/collection/receipt times, units, freshness, source, release/generation, process identity and error/unavailable reason. Stale known values remain visibly stale; missing never becomes healthy zero. Combined snapshots retain each input's age. Policy names required inputs, objective and alternatives, then emits an explainable proposal without performing effects.

Controls include inspect; money/XP objective; selected release; subsystem desired state; temporary target/activity override; resource/cash/recovery budgets; proposal acceptance where already authorized; pause/drain/stop and rollback. Show base policy, durable preference, every temporary override, precedence, setter/source, reason, creation/expiry, revision and effective value. Emergency pause and authority constraints dominate all overrides. Local and game clients share validation and acknowledgements; conflicting expected revisions reject visibly. Durable desired state survives source sync, reconnect and compatible upgrades.

All game and local messages use one versioned event interface: event ID, producer sequence, occurrence/receipt time, environment, source/process, release/generation, level, kind, correlation/logical action/attempt IDs, human message and relevant decision inputs/results. Record every variable in each decision predicate, including authority and denied alternatives. Render human lines from structured fields; do not maintain separate handwritten status/log interpretations.

Each producer owns a stream, or sends to a proved single writer. Use game-supported `.txt`/`.json` files, bounded segments and contiguous acknowledged export to durable local storage. At-least-once transfer plus event-ID deduplication must survive disconnect, partial local write, restart and rollover. Specify maximum segment/payload, polling/CPU cost, outage capacity, local retention and free-space alarms. Preserve occurrences within that capacity; if unexported capacity fills, display evidence degradation and stop new effects that cannot be durably recorded. Never silently drop events or promise unlimited disconnected retention. A minimal bootstrap/emergency logger may bypass the normal path only to report its failure and later import that record; it must not recurse.

Tail equivalence uses kind, level, normalized message and relevant context, excluding occurrence IDs/times only for equivalence. Repeated identical informational state may show count, first/last and periodic summary. Changed inputs, decisions, warnings and errors remain individually visible. The full stream retains occurrences; console, dashboard, tail, file and Remote API are projections. Finite/orphaned tails cannot establish complete evidence.

## 7. Investment, stock and automation ROI

Every continuing automation has a card beside health: capability/release, objective, RAM, event-loop/CPU cost, machine/operator time, output and progress delta, baseline, marginal benefit, confidence/sample window, confounders, opportunity cost, budget/stop rule and next review date. Unknown is an honest result that limits expansion. Diagnostics may use finite cost/outcome records rather than a permanent process/card. Displays/recovery justify cost through operational outcomes, not artificial dollar attribution.

Cloud proposals contain current and added usable capacity after reservations, purchase cost, cash reserve/total budget, server slot/cap effect, projected marginal money and XP, model assumptions/window/confidence, opportunity cost, estimated payback, expiry and post-purchase measurement. Zero/negative money benefit has no finite payback; XP is not silently priced as dollars. Purchased game servers add RAM, not independent renderer CPU. Recheck price/resources/policy immediately before an authorized purchase; measure time to useful work, actual capacity and benefit afterward. Unknown purchase outcome requires inventory reconciliation before retry.

Stock coverage is mandatory even while authority is held. Preserve and assess existing long-only behavior, API access checks, entry signal, exits, adaptive cap and position state; do not infer shorts or orders. Stock monitoring and pure strategy/accounting must be independently useful without a live executor. Distinguish missing access, unavailable forecast, stale market tick, no positions and unreadable ledger. Reconcile actual positions and cash with saved state, and mark imported/manual positions or uncertain cost basis honestly.

Stock tests must cover fees/spread, execution price versus a post-trade quote, aggregate simulated capital reservation, multiple symbols, rejected/zero-result calls, crash after action but before persistence, unknown outcome, manual position changes, duplicate command, portfolio cap change, loss/exit behavior, reset identity and missing/corrupt ledger. Build proposal simulation that deducts each proposed purchase from a shared budget. Accounting uses executed quantity/price/cash evidence and documented fees, not a fresh quote assumed to describe an earlier execution. Report realized and unrealized P&L separately, equity, basis quality, fees, turnover, exposure, drawdown, and cash/cap reservations.

Eventual order intent includes symbol/side/quantity, price/budget assumptions and freshness, expiry, position precondition, aggregate cap/reserve, explicit authority and logical ID. Re-read positions/budget at execution; correlate receipt with actual position changes. Do not promise exactly-once orders from file transport. The approved exit/hold policy must be explicit; stopping, rollback and “emergency recovery” cannot liquidate automatically. A capital decision is concrete: named strategy/version, environment, funds/cap, allowed buys/sells, loss/exit policy, duration and stop rule. Complete all currently authorized planning, pure implementation and tests before seeking the authority needed for the next restricted step.

IPvGO requires useful faction-reputation/progression gain, not games or wins alone. Hold faction/membership, board size, algorithm and budget constant in comparisons; record streak/favor, game completion, event-loop delay and displaced MCP output. Use a finite trial, initially no more than 30 completed games or two hours, with predeclared benefit and responsiveness criteria. An inconclusive interval does not establish value; any extension is a finite new proposal. Do not repeatedly reset trial budgets. Drain an in-progress game unless a responsiveness emergency requires stopping; record forfeiture and apply its authority boundary. Other capability ROI should use actual useful outputs: newly usable rooted capacity, accepted contract rewards, Darknet progression/loot, skill/faction gain net of fees, readiness accuracy, and share's marginal gain while actual faction work runs.
