# BitBurner rewrite plan — evidence before authority

Planning status: 2026-09-07. This is a code-free implementation plan, not an implementation or deployment authorization. Its first deliverable is a separate documentation-and-test coordination artifact. The current farming system remains the baseline until replacement capabilities earn their way through the gates below.

The recommended rewrite is a narrow control foundation around proven gameplay behavior: consistent observations, release identity, durable events, explicit desired state, and one owner of process reconciliation. Keep the existing scheduler behind an adapter initially. A scheduler replacement, external Go engine, new trading behavior, and a broad subsystem rewrite are separate proposals justified by measured shortcomings, not prerequisites for reliable operation.

### Remote API: both ends, with version limits

The local implementation is `tools/bb_remote.py`: `RemoteApiServer`, `BitburnerApi`, `TriggerDaemon`, and `run_selftest`. Its mock verifies basic file round trips, request correlation, incremental sync/pull, missing files and moved-directory alarms. It does not establish Netscript lifecycle behavior, save identity, browser handshake behavior, or atomic release delivery.

The upstream game implementation inspected is [MessageHandlers.ts](https://raw.githubusercontent.com/bitburner-official/bitburner-src/dev/src/RemoteFileAPI/MessageHandlers.ts), [Remote.ts](https://github.com/bitburner-official/bitburner-src/blob/dev/src/RemoteFileAPI/Remote.ts), and [RemoteFileAPI.ts](https://github.com/bitburner-official/bitburner-src/blob/dev/src/RemoteFileAPI/RemoteFileAPI.ts). The retrieved dev sources are not proof of the installed Steam/browser build and were retrieved from different cached dates. P02 must pin one coherent revision and compare it with the actual game versions.

The inspected handlers validate file paths/extensions/hosts, write content, and return success; file writes do not themselves supply an application action protocol. The bridge therefore needs a narrow in-game command consumer for execution and acknowledgements. The inspected connection class schedules retry after an unexpected close when reconnection delay is positive and cancels retries for intentional closure. This contradicts the Python history's unconditional claim that the game never reconnects automatically. Browser policy, settings, and installed version must be reproduced before deciding whether any reconnect workaround is necessary. The Python Private Network Access comment and manifest's claim that browser Remote API cannot work also conflict; neither is accepted as settled platform truth.

## 2. Operating contract and boundaries

Success means the operator can answer from the system: what is observed and how fresh it is; what is desired and which override wins; why a proposed action is allowed; which source, delivered files, and process generation are involved; what actually happened; what benefit it produced; and how to pause or roll back it.

The browser save is disposable integration infrastructure, but must be visibly identified and separate from Steam, including storage/profile, connection endpoints, local telemetry roots, release channel, and automation profile. Record game version, save/session fingerprint, daemon identity, and browser identity before a test. A copied save needs an explicit test marker after import; inherited player identity alone may not distinguish the copy. Never point a test daemon at the production checkout or rely on the full existing manifest as a safe test profile: it includes stock and purchase scripts.

Steam remains the protected live environment. Planning and research do not authorize changes to its source watcher, connection settings, files, processes, or progress. During implementation, routine reversible, tested operations already authorized by the working agreement remain ordinary agent work. A new control path reaches Steam only after the corresponding browser evidence and a recorded policy decision within existing authority. Explicit stop-list actions still require Ken's approval. This is an engineering evidence sequence, not a replacement governance tier system.

A deterministic in-game reconciler should own process execution and continue its last valid authorized plan if the local observer disappears. The local controller may observe, propose, and submit typed desired-state changes within its policy; it must not become a second process supervisor. Optional AI stewardship may explain and propose. It is not required for routine recovery and cannot modify its own authority or choose new goals. Existing workers may finish during telemetry loss; stale observations never justify new destructive reconciliation.

Treat stop, drain, disable, and rollback as distinct controls. Stop accepting new commands immediately on a pause. Drain allows authorized in-flight game actions to finish if the deadline permits. Emergency stop kills only owned PIDs with matching host/generation identity. Rollback deploys the prior verified release under a **new** generation and restores compatible desired state; it does not restore or import a Steam save. Purchases, contract attempts, augmentation installation, and abandoned Go games may be irreversible and cannot be described as “rolled back.”

## 4. Foundation contracts to make executable

### Observations and events

Observed state includes schema version, environment/save epoch, collection and receipt times, source release and runtime generation, process identity, measurement units, quality/freshness, and unavailable/error reasons. A snapshot may contain inputs collected at different times; policy lists which are required and rejects stale required inputs. Preserve last known values visibly as stale, never as current zeroes. Prefer monotonic durations inside a process; retain wall-clock timestamps and source sequence for cross-process evidence.

One event interface covers both game and local messages, with schema version, occurrence/receipt time, environment, source/component, process/run, release/generation, severity, kind, stable event ID, source sequence, action/correlation ID, message, and all decision-predicate inputs. Human lines are rendered from those fields. Early boot/logger failure may use a minimal emergency projection with a visible degraded-logging indicator; it must not recursively call the failed logger or claim durable receipt.

Each producer owns its stream or sends through a demonstrated single writer; avoid concurrent read-modify-write of shared game files. Use game-supported `.txt` or `.json` extensions. The game keeps a bounded spool; the local controller archives acknowledged events and detects sequence gaps and duplicates. Replay is at-least-once with deduplication by event identity, not a claim of exactly-once transport. Define segment size, rotation, acknowledgement, retransmission, archive retention, free-space alarms, and outage capacity in P01. Preserve every occurrence within the supported capacity; when that capacity is exhausted, visibly stop new automatic actions whose evidence cannot be recorded rather than silently dropping occurrences. No finite spool promises unlimited disconnected retention.

Tail equivalence uses event kind, severity, normalized message, and relevant context; ignore occurrence timestamps/IDs only for equivalence. Heartbeats with identical state may coalesce into count plus first/last time and periodic summary. Changed inputs, decisions, warnings and errors stay individually visible. The raw stream retains occurrences even when rendering coalesces them. Dashboard, tail, terminal, file and Remote API projections must replay to the same facts. Tail height and orphaned windows cannot establish complete evidence.

### Release and process identity

A release is an immutable dependency-complete source artifact with canonical paths, byte hashes, schema/protocol compatibility and a content digest. Keep runtime controls and generated telemetry outside it. Deliver files to an isolated release namespace where game imports permit it; explicitly test import resolution and RAM accounting before committing to that layout. Verify all delivered bytes before activation. Every long-running process reports a boot-captured release and generation, never an identity freshly read from a mutable file after it starts.

Display source artifact digest, delivered verified digest, and each process's captured digest/generation together. A shared manifest file reporting the new digest cannot prove an old process is running new code. Only the reconciler retires superseded owned processes, and it must confirm their termination before admitting a conflicting owner. Account for remote hosts, in-flight actions, PID reuse, missing RAM, partial copy, crashed startup and dependencies loaded at process start. Unknown/foreign processes are surfaced, not swept away.

### Controls, authority and reconciliation

Minimum controls: objective money/XP; subsystem desired state; selected release; observing/proposing/acting mode; temporary target override; approved resource/recovery budgets; pause/drain/stop; and the plain-language money-switch protection. Expose effective value, default, every override, provenance/setter, reason, creation time, expiry, revision, and observed conformance. Higher-precedence emergency pause and authority restrictions constrain all overrides; a target override cannot grant capital authority. Define base policy → durable preference → temporary override resolution explicitly, with restrictions applied at the final gate.

Local and game controls use the same validation and command contract. Concurrent edits use expected revision and receive a visible conflict instead of last-writer-wins. Accept a command only after durable recording and validation; provide visible confirmation of its final result. Preserve issued IDs and outcome state across controller/game restarts. An expired command cannot execute after reconnect. Delivery timeout means unknown until readback and process inspection reconcile it; retries reuse the same logical ID. Expiry during disconnected operation follows one specified rule on the game side, not independent clocks resolving different policies.

Every action names environment, desired revision, release/generation, target, preconditions, authority source, resource cap, cooldown, idempotency key, reason and deadline. The gate is evaluated at execution time as well as proposal time. Runtime code cannot broaden its allowlist. Recovery is bounded by attempts per window and an overall incident budget; persistent cooldown alone must not permit infinite retries. Record request, execution, evidence and final disposition. Conformance includes denied, delayed, unknown and impossible states.

### Investment and subsystem value

An investment proposal names current/added RAM, executable capacity after reservations, API purchase price, projected marginal money/XP rate, model assumptions, confidence/window, payback, opportunity cost, cash reserve, total budget and server cap. Zero/negative estimated money gain has no finite payback; XP gain is reported in XP units and cannot be silently converted into dollars. Revalidate affordability and authority immediately before execution. Record post-purchase identity and resource/income observations; a hostname receipt alone does not establish benefit. Purchase authority starts propose-only and is a separate visible policy from health recovery.

Every automation gets an ROI card beside health: current objective, RAM and CPU/event-loop cost, elapsed human/machine time, output/progression delta, baseline, marginal benefit, uncertainty/window, opportunity cost, budget, stop rule and next review date. “Unknown” is valid and constrains ongoing allocation. Measure MCP income/XP opportunity cost when another subsystem occupies RAM. Contracts report accepted rewards and remaining-attempt risk; rooting reports newly usable capacity; HUDs report observation cost; Darknet reports useful progression and response cost rather than counts alone.

For IPvGO, hold faction, membership, board size, algorithm and think budget constant within each comparison. Use faction reputation/progression deltas and streak/favor mechanisms, not wins alone. Record event-loop delay and MCP throughput alongside Go move time. Start a capped browser experiment; compare a fixed baseline and one changed variable with matched save/profile where practical. Require a predeclared window and minimum useful benefit before ongoing allocation. For an initial experiment, cap at 30 completed games or two hours, whichever comes first; if insufficient for a useful interval, label inconclusive and propose a finite extension. Do not grant ongoing capacity by repeatedly resetting the experiment budget. Finish an in-progress game when stopping unless the responsiveness stop rule requires immediate termination; any forfeiture is recorded and subject to the environment's reset/progress boundary.

## 7. Work packages and dependency graph

Each package is one bounded agent assignment. Its owner reads the input documents before changing anything; produces the named artifact; updates technical/operator documentation in the same implementation change; runs only the prescribed relevant checks; and finishes with the handoff record below. Split a package if it requires unrelated interfaces or cannot name one acceptance gate. Package IDs describe work, not governance ranks.

Common authority shorthand: **local** = isolated files, docs and local tests; **browser** = only the identified disposable environment under its profile; **Steam** = bounded existing-authority actions after preceding gates; **proposal** = no spending, reset or restricted activation. Local rollback preserves the prior accepted artifact; browser rollback uses its saved test baseline and owned-process cleanup; Steam rollback uses the prior release and policy without restoring progress.
